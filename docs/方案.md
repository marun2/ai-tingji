# AI听记平台 方案

2026-11-24 · 和用户（中台管理员）几轮沟通后定下的方案，还没开始开发。

## 要解决的问题

公司的会议、面试、通话都用钉钉 AI听记记录，之前靠人工导出 Word、手动归到各部门文件夹。目标：

- 新的听记由管理员定期导出 Excel 上传，平台自动整理、自动分类到部门
- 做成一个知识库：按部门浏览、打开预览、搜索、用大模型提问
- 每周自动出周报、每月自动出月报（推送时间以后再定）
- 老板（董事局）能看全部；指定的部门负责人只能看「研发市场销售」

## 形态

中台上的一个**带后台的应用**（Python，参照 `server/content/templates/python-fastapi`，做法同 KA 销售平台）。
中台只负责飞书登录和「谁能打开」（可见范围 = 董事局 + 指定同事），其余全部在应用里。

**例外（用户 2026-11-24 明确决定）**：本应用**单独接大模型**，不走中台“全公司只接一个大模型”的规则；也**不接**中台的问一问和飞书机器人（以后再说）。后来接手的人不要把它改回走中台。

## 数据来源

- 管理员每次只上传**新的**听记 Excel（钉钉导出，工作表「听记汇总」）
- 列：标题、创建人、开始时间、时长(分钟)、关键词、AI摘要、待办事项、转写原文、听记链接、所属组织
- **听记链接**（`shanji.dingtalk.com/app/transcribes/<ID>`，在单元格超链接里，显示文字是 view）作为唯一键去重，重复上传不会重复入库
- 只收 **2026-08-14 之后**的数据；只收名单里的主体，名单外的（如上海璟瑞企业管理有限公司）不导入
- 没有标题/时间的行丢弃（首份 Excel 第 1163 行以后的 1,373 行是删除时没删干净的残留）
- 「会议录制：xxx」和同名、同创建人、开始时间相近的听记是同一场会，合并
- 转写原文被 Excel 截断在 32,767 字的，标记“原文不完整”，问答时以摘要为准
- 空记录（摘要和原文都很短）不进知识库，导入后列清单给管理员
- 首份 Excel 有效数据：1,132 场会，2026-08-14 至 11-21，约 1,400 万字

## 目录（知识库）

```
上海食品
  ├ 研发市场销售   ← 研发、市场、销售已合并成一个板块，也包括各子公司的业务会
  ├ 人事
  ├ 财务
  ├ IT
  └ 董秘办
每日博士 / 大健康 / 均瑶云商 / 均瑶润盈 / 衢州食品 / 均瑶宜昌 / 泛缘 / 测试部门
（每个文件夹下再按月份分）
```

- 主体按「所属组织」直接对应（规则）
- 部门由大模型读摘要判断，**可以多个**（一场会可以同时在财务和研发市场销售）
- 同时打会议类型（例会、经营分析、面试、客户拜访、外部讲座、通话……）和敏感等级
- **进「研发市场销售」要保守**：面试、人事、财务类不自动放进去；拿不准的进「待确认」，只有董事局和管理员能看，管理员确认后再放
- 首批可以用用户之前手工整理的 Word 文件夹（约 2,400 个文件）检验分类准确率

## 功能

1. **导入**：上传 Excel → 去重、清洗、分类、抽取、切段、向量化；显示进度和结果（新增几场、跳过几场、待确认几场）
2. **知识库浏览**：左边目录树（没权限的文件夹不显示），中间预览（摘要 / 原文 / 待办，带时间、创建人、时长、关键词）
3. **搜索**：关键词 + 向量混合检索，结果显示命中的段落
4. **提问**：右侧对话框，范围可选“我能看到的全部”或“当前文件夹”；回答只依据检索到的会议内容，下面列出出处，点开跳到原文对应段落
5. **导出**：勾选文件或文件夹 → 打包 zip 下载；每场会一个 Word，**摘要和原文在同一个文件里**，保留文件夹结构；只能导出自己有权限的
6. **周报 / 月报**（推送时间、是否先审核再发，都以后再定）：
   - 周报：本周概览、经营数字（来自会议发言，标“待核实”）、重要决议、待办跟踪（新增 / 完成 / 逾期）、风险与问题、外部动态（竞品客户合作方）、下周关注；每条带出处
   - 月报：在周报基础上加四周趋势、各主体 / 部门对比、月度专题、跨月未解决的问题
   - 按权限裁剪：董事局收全公司版，部门负责人只收研发市场销售的内容
7. **管理**：权限名单、待确认队列（改归属）、模型设置、导入记录

## 权限

| 谁 | 能看 / 能问 / 能导出 |
|---|---|
| 董事局成员（中台「组织」页映射为董事局的人） | 全部 |
| 管理员（用户本人） | 全部（要处理待确认） |
| 管理员指定的部门负责人（在应用管理页添加） | 只有「研发市场销售」 |

- 身份来自中台转发的 `X-Zt-User-*` 请求头
- 检索时**先按权限过滤再交给大模型**，大模型看不到提问人无权看的内容
- 中台可见范围设为“董事局 + 指定同事”，其他人在中台看不到这个应用

## 数据存放

| 内容 | 位置 |
|---|---|
| 会议、分类、抽取结果（决议 / 待办 / 风险 / 数字）、报告、权限表、模型设置 | 中台共用 PostgreSQL，本应用 schema（`app_<标识>`） |
| 上传的 Excel 原件、向量索引 | 应用目录 `/app/data`（`data/app-data/<标识>`） |

- 用户明确**不要专门备份**（怕占空间）。中台每天的 `pg_dumpall` 本来就会带上会议文字（几十 MB，保留 3 份）；向量在 app-data 里，不进备份，丢了可以从文字重新生成
- 真正的兜底是用户电脑上的历史 Excel，重新导入即可恢复，已提醒用户不要删
- **不放** `dw` 公共只读区（所有应用都能读，面试等内容不能放）；不放飞书多维表格（原文太长、权限不够细）
- 规模：首批约 1.7 万段（每段约 800 字），向量约 70MB；按现在的节奏一年约 250MB

## 模型

- **大模型**：先用和中台问一问同一家——极策云中转站 `api.jiceapi.com`，模型 `deepseek-v4-flash`（OpenAI 兼容接口）。
  - 在应用「管理 → 模型设置」里由用户自己填地址、模型名、密钥（密钥不经过 Claude）
  - 按任务分开配置（分类抽取 / 提问 / 报告），随时可换；建议给本应用单独建一个令牌，用量单独统计、可单独停用
  - 平台做好后，用老板常问的 10 个问题在两三个模型上各跑一遍，对比后再定
  - 备选：熊猫API（按次付费，输入越长越划算，适合批量分类抽取；需先确认单次输入上限和 8 额度合多少钱）
  - 数据安全：所有发给大模型的内容会经过中转站。用户 2026-11-24 选择全部走中转站
- **向量模型**：**放在服务器本地跑**（用户选定），全部原文不出服务器
  - 两家中转站都没有向量模型
  - 候选：`bge-m3`（中文效果好，1024 维，模型约 2.2GB，运行约需 2～3GB 内存）；内存不够时用 `bge-base-zh-v1.5`（约 400MB）
  - 应用内存上限默认最多 2048MB（`zhongtai.json`），用 bge-m3 需要用户在服务器 `/opt/zhongtai/data/deployer.json` 的 `unlimited` 里加上本应用
  - 模型文件放进 `Dockerfile.base`，从 ModelScope 下载（服务器访问 HuggingFace 可能不通）
  - 首次向量化 1,400 万字在 4 核 CPU 上预计一到几个小时，之后每次增量几分钟

## 中台要配合的改动

- 暂无（应用自己接大模型、不接问一问）。以后要给周报月报推飞书消息时，需要中台加一个“应用发飞书消息”的接口

## 开发顺序（待用户确认后开始）

1. 导入 + 去重清洗 + 分类 + 知识库浏览 + 权限（用历史 Word 检验分类准确率）
2. 本地向量化 + 混合检索 + 提问 + 导出 Word
3. 抽取（决议 / 待办 / 风险 / 数字）+ 周报月报
4. 待定：推送、报告审核、接问一问 / 飞书机器人
